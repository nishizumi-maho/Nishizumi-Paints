# Nishizumi Paints 7.3.4

Release date: 2026-09-26

## Drivers joining a Practice no longer re-download everyone

In a Practice session the paints of the whole field were being deleted and downloaded again every time someone joined.

The cause was the check that stops a paint pass when the session changes. It also counted a driver joining as a change, so a join during a pass cancelled it, removed every paint already saved, and started over for all drivers. A full pass on a 55-driver server takes about a minute, and most of that is the online fallback stage, so on a busy server a new join landed inside almost every pass and the cycle repeated.

From 7.3.4:

- A driver joining or leaving never interrupts the running pass. It finishes for the drivers it started with, and the next pass fetches only the new drivers. The log shows `Session roster changed inside the same session ...: +1 target(s)` followed by a pass for just that driver.
- Paints already applied stay in place. Nothing is deleted when someone joins.
- The pass is still cancelled, as before, when the session itself changes (new session or subsession), when its Trading Paints context changes (team racing, time of day, series, league, custom numbers, track, superspeedway), or when the session ends.
- A fixed paint applied from the Session tab is no longer rejected just because a driver joined a moment earlier.

## Faster manifest stage when a Trading Paints host is down

Nishizumi Paints asks two Trading Paints hosts for each driver's paint list. One of them, `dl.tradingpaints.com`, is currently failing its TLS handshake. Every driver tried it three times with backoff before moving to the working host, which delayed the first download of every pass by about 15 seconds on a full server.

Now a host that cannot be reached at all is skipped for that driver right away, and the working host is tried first for the next 10 minutes. The log records it once:

`Trading Paints manifest host dl.tradingpaints.com could not be reached (SSLError); using the other host first for 10 minutes.`

HTTP errors and slow answers still get the normal retries, and if the working host fails too, the other one is tried again.

## Faster online fallback

When a driver has no Trading Paints paint, the public showroom fallback picks a random car, helmet, or suit from a Trading Paints showroom list. Each list page takes a few seconds to answer. The app fetched those pages one at a time, and kept them only for the current pass, so every driver who joined a running session paid for them again: about 13 seconds for one driver needing a car, a helmet, and a suit.

Now:

- The pages a pass needs are fetched in parallel before it starts. The log shows `Trading Paints public showroom lists ready: N list(s) for M pool(s) in X s`.
- Pages are kept for 15 minutes for the whole app. A driver joining a running session is usually covered from pages already in memory.
- Empty or failed answers are never kept, and the duplicate and recent-history rules are unchanged.

Measured against the live Trading Paints servers:

| | 7.3.3 | 7.3.4 |
|---|---|---|
| Field of 8 drivers needing car, helmet, and suit | 62.8 s | 28.4 s |
| One driver joining afterwards | 12.8 s | 1.5 s |

## Fewer texture reloads

A car's paint, spec, helmet, and suit arrive a moment apart. Each file used to trigger its own iRacing texture reload for that car after 0.2 seconds, so the same car was often reloaded three or four times within a second. Reloads are now grouped per car for one second, so each car is normally reloaded once per pass.

## Randomize active AI roster works

The **Randomize active AI roster** button on the AI tab only wrote an error to the log: the feature behind it had never been written. The online fallback log even pointed people at it.

Now the button:

- reads the active AI roster you already synced from Trading Paints
- gives every driver a random car paint (with its spec map), helmet, and suit from your RandomPool and AI livery folder, following your favorite and blocked random paints
- saves the result as a new local roster named `<roster> (random)`, leaving the original roster unchanged

Paints only repeat once every paint for that car has been used. A driver whose car has nothing in the RandomPool keeps the original roster paint. Clicking again replaces the `(random)` roster with new picks, even while it is the roster selected in iRacing. If the RandomPool has nothing for the roster's cars at all, the previous `(random)` roster is kept and the log says why.

Select the `(random)` roster in iRacing and recreate the AI race to see the paints.

## Other fixes

- The legacy showroom helmet and suit sync no longer crashes when it is cancelled while waiting for the Trading Paints request cooldown.

## Validation

- A service-loop test drives the real session loop against a simulated iRacing SDK: a driver joining mid-download results in one pass for the original field and one pass for the new driver, with no paint deleted. On 7.3.3 the same test shows the pass cancelled and the whole field downloaded again.
- Tests confirm a new subsession or a context change still cancels the pass, and a join or a leave does not.
- Tests cover the manifest host fallback: an unreachable host is tried once, later fetches start with the working host, HTTP errors keep their retries, and the last host left still gets all its retries.
- A test confirms a car receiving four files 0.3 seconds apart is reloaded once.
- Tests cover the showroom page cache: a page is fetched once, each source, page, and pool is cached separately, expired and empty pages are fetched again, and after the prefetch the helmet and suit picks make no request at all.
- Checked in a live iRacing Practice with 31 drivers: 1 full pass, then 10 passes of one or two new drivers each, no cancelled pass, and no paint deleted.
- Measured against the live Trading Paints servers, fetching 20 drivers' manifests in parallel went from 10.9 seconds to 2.7 seconds.
- Tests cover the randomized AI roster: every driver gets a RandomPool car, spec, helmet, and suit; paints do not repeat while unused ones remain; a second click replaces the roster, including when it is the active one; an empty RandomPool keeps the previous roster; and the AI tab button runs without error.
- Full suite: 138 tests, all passing.
