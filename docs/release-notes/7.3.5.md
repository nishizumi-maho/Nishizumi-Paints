# Nishizumi Paints 7.3.5 (experimental)

Release date: 2026-10-10

This is an experimental build. It fixes the startup mode selector that kept coming back, and it makes the console-only (headless) mode check for and install updates by itself. Please report anything odd about starting the app or updating it.

## The startup mode selector remembers your choice

Some people saw the selector (normal window or console only) again and again, even after picking a mode with **Remember this choice** ticked.

The cause was the order of two steps at startup. When the app was already running, typically in the tray after starting with Windows, opening it again showed the selector first and only then noticed the copy that was already running. The new choice was saved, but the running copy still held the settings it loaded earlier. The next time it saved any setting, including ones it saves by itself during a session, it wrote the old startup mode back and the choice was gone.

From 7.3.5:

- Opening the app while it is running brings the running copy forward. The selector is not shown. Hold `Shift` while opening the app to choose a mode anyway.
- The startup mode is saved on its own, without rewriting any other setting, and a running copy no longer writes an older startup mode back.
- Starting with Windows never stops at the selector. It uses the saved mode, or the normal window when none is saved.
- **Remember this choice** is ticked by default.
- `settings.json` is replaced in one step, and a read that lands while another copy is saving is tried again, so nobody sees a half-written file and falls back to default settings.
- After an update, the app reopens in the mode it was running in instead of asking again.

## Console-only mode checks for updates and installs them

Before, only the window checked for updates. Someone using only the console never heard about a new version.

Now the headless service:

- checks GitHub about 20 seconds after it starts and then every 6 hours, following **Check for updates automatically**, and tries again after 15 minutes when a check fails
- announces a new version in the console and with a Windows notification
- installs the update when you click the notification: it downloads the installer, checks its SHA-256 digest against the one published with the release, runs it, and starts the console mode again on the new version
- does all of that without asking when **Install updates automatically** is on

The console shows what happens, for example:

```
WARNING Update available: v7.3.6 (you have 7.3.5).
WARNING Click the Windows notification to install it now, or turn on 'Install updates automatically' in the app settings so the headless service installs new versions by itself.
```

A window attached to a running headless service leaves updates to that service. Installing from the window hands the update to the service and closes the window, and the window closes on its own if the service shuts down to install an update.

The headless control server gained `check_updates` and `install_update`, and `status` now reports `update_state`, `update_message`, `latest_release_tag`, and `update_available`.

Experimental builds are pre-releases, which the updater never offers, so this one is installed by hand. Once it is installed, both the window and the console mode are told about normal releases newer than 7.3.5.

## Validation

- 45 new tests cover the startup mode and the headless updates:
  - the startup mode is saved without touching other settings, and an unreadable settings file is not overwritten
  - a running copy saving settings it loaded earlier keeps the startup mode chosen later by another launch, which is the bug behind the selector coming back
  - opening the app while it runs brings it forward without the selector, a sign-in launch never asks, `Shift` still asks, and command line switches still win
  - a read during a save is retried, and saving leaves no temporary files behind
  - the headless service announces a new version once, installs it on a notification click or by itself, relaunches with `--nogui`, does not retry a failed automatic install, points builds that cannot install to the download page, retries a failed check sooner, and lets only one install run at a time
  - the window leaves automatic installs to an attached headless service, hands a manual install over, and closes when the service leaves to install
- The real headless entry point was run in isolation from the saved mode alone, without `--nogui`. It found the published v7.3.4 against a local version set to 7.3.3, logged it, sent the notification, reported it through `status`, and stopped cleanly through `stop`.
- A real Windows notification was shown from the tray icon.
- Full suite: 189 tests, all passing.
